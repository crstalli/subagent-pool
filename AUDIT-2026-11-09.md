### Live host mechanics (static `index.js`, verified by reading all 724 lines)
- **Guard**: `ctx.on('tools/pre-execute', …)` waterfall. `subagent`/`subagent_fork`: resolve route (explicit `provider`/`model` args, else `defaultRoute()` = `agent-default-model` setting); unknown route → deny; `reasoning_effort` above route `maxThinking` → deny; `cap 0` → deny; at capacity → **FIFO queue** (timer service, abortable via `exec.signal`, `queueMaxWaitSec` timeout, `queueMaxLen` overflow deny). `workflow`/`ralph`: total cap only, queue on `total`.
- **Accounting**: `agent/created` / `agent/status` / `agent/disposed` / `agent/error` into a `tracked` Map; leaf reads only. Soft race window documented (guard decides before `created` is booked).
- **Steering**: `systemPrompt.section('subagent-pool', order 1000)` renders route list + queue state into every session while active.
- **Namespace**: on activation writes `subagent-model-selection = {enabled:true, allowedModels: routes}` (restores previous value on dispose). Uses the full `settings` service via `ctx.inject(['settings'])` → two-arg `update(ns, patch)`, so the skill's sandboxed-handle `TypeError` issue does **not** apply to this static plugin.
- **HTTP API** on the web server: `GET /subagent-pool/status`, `/subagent-pool/models`, `/subagent-pool/model-info?provider&model`, `GET /subagent-pool/configure?config=<base64>` (validates v3, atomically writes JSON, hot-applies, flushes queue on disable).
- **Loader `config` is ignored**: `apply(ctx, config)` never reads `config` — pool enabled state comes **only** from the JSON. (The uncommitted repo change to `cordis.patch.yml` `enabled:true/false` is therefore cosmetic; installed copy says `enabled:false`, repo says `enabled:true` — drift to be aware of.)

## 7. How to configure the pool (the supported path)

1. **GUI (preferred):** Web GUI → Settings → Plugins tab → **Subagent Pool** card (registered id `subagent-pool`, key `subagent-model-selection`; also mirrored in the Agent-presets configurable slot). It polls `/subagent-pool/status`, lists providers/models from `/subagent-pool/models`, per-model effort ladders from `/subagent-pool/model-info`, and Save calls `/subagent-pool/configure` → validates v3 → atomically writes the **installed** `subagent_pool_config.json` → hot-applies.
2. **Agent/HTTP:** `GET http://127.0.0.1:3080/subagent-pool/configure?config=<base64 of full JSON>`.
3. Do **not** edit the repo JSON expecting a live effect — the live file is `~/.dsh/profiles/web/node_modules/dsh-subagent-pool/subagent_pool_config.json`; repo changes ship on next git install.

  "enabled": true,
  "totalCap": 2,
  "queueMaxWaitSec": 300,
  "queueMaxLen": 20,
  "routes": [
    {
      "provider": "arc",
      "model": "qwen3.8-27b-k4_xl-thinking",
      "cap": 1,
      "tier": "deep",
      "maxThinking": "high",
      "profile": { "thinking": "high", "speed": "medium", "instructions": "high-level ok",

    },
    {
      "provider": "ollama-local",
      "model": "rtx",
      "cap": 1,
      "tier": "easy",

### 9.4 NEW FINDING — `/subagent-pool/configure` validates shape only, not registry membership

`validateConfig` (`index.js:78-113`) checks: totalCap positive int; routes non-empty array; provider/model non-empty strings; cap non-negative int; maxThinking in the effort ladder or `''`; no duplicate `provider/model`; queue bounds. It does **not** check the provider/model against DSH's live registry, nor cap vs totalCap. Demonstrated on 3087: `configure` with `provider:"no-such-provider"` → `ok:true`; `cap:5` with `totalCap:1` → `ok:true` (and routes are **replaced wholesale**, not merged). This is exactly the gap `subagent-pool-SYNC-INSTRUCTIONS.md` §5/§6 describes ("server rejects caps for unknown models" — planned, not yet implemented). Spawn-time enforcement is still fail-closed (guard denies unknown routes), so this is a hygiene/UX bug, not a bypass. Note the configure handler **does** preserve `queueMaxWaitSec`/`queueMaxLen` from current state when the request omits them (`index.js` configure handler), so a Save from today's card doesn't drop queue settings — but the card has no queue fields to edit them (the §5 UI gap stands).

### 9.5 SYNC-INSTRUCTIONS step 1 answered (registry read API)

The live registry read API already exists on the `llm` service and is what the plugin itself uses: `llm.listProviders()` (`index.js:554`) → `llm.listModels(providerId)` per provider (`:566`) → `llm.resolveModelInfo(provider, model)` for the effort ladder (`:595`). ### 9.7 RESOLVED 2026-11-10 — pool entry is now a first-class *configurable plugin entry* (docs-sanctioned `Config` schema); branch `fix/settings-ns-and-bundle-card` @ 41a10f7 (pushed)
