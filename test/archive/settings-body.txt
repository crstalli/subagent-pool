1. --no-kv-offload — your reading is exactly backwards

In llama.cpp, "offload" always means "move to the GPU" (it's the same word as in -ngl 99, "offload 99 layers to GPU"). "offload to RAM" isn't a thing in this codebase — RAM is the default resting place, and offload is the act of taking it out of RAM. The chain of code:

Step 1 — common/common.cpp:1745:

cpp
Copy
cparams.offload_kqv = !params.no_kv_offload;   // default (no flag) = true

Step 2 — src/llama-kv-cache.cpp, per-layer KV buffer allocation (this is the actual device choice):

cpp
Copy
const char * dev_name = "CPU";
ggml_backend_buffer_type_t buft = ggml_backend_cpu_buffer_type();

if (offload) {                          // offload == cparams.offload_kqv
    auto * dev = model.dev_layer(il);   // your Arc, SYCL0
    buft = ggml_backend_dev_buffer_type(dev);
    dev_name = ggml_backend_dev_name(dev);
}

So: no flag → KV allocated on the GPU. Your --no-kv-offload → KV allocated on the CPU (system RAM).

Step 3 — src/llama-graph.cpp:2725, the comment says it outright:

cpp
Copy
if (!cparams.offload_kqv) {
    // all nodes between the KV store and the attention output are run on the CPU
    ggml_backend_sched_set_tensor_backend(sched, cur, backend_cpu);
}

So the flag means "don't offload the KV to the GPU" = "keep the KV in RAM." It is precisely the flag that created your RAM problem, not the flag that would avoid it.

2. --load-mode none — this also does not bypass RAM

There is no disk→VRAM path in llama.cpp; weights always pass through host memory. The flag only chooses which kind of host memory (src/llama-model.cpp):

auto (default) = mmap: the file is memory-mapped, and the mapped region is handed to the backend via ggml_backend_dev_buffer_from_host_ptr(dev, addr, ...) (line ~1784). Those pages are file-backed — they count as "used" RAM in Task Manager but the OS can evict/reclaim them under pressure.
none: use_mmap = false → the loader reads the entire 16.8 GB file into a private RAM buffer — note the comment at line 1862:
cpp
Copy
// without mmap, load non-host buffers first: their tensors go through a staging buffer, ...
That's a hard, non-reclaimable copy. It's the most RAM-hungry mode, not the leanest.

Your screenshot is the empirical proof: steady-state 22.5 GB RAM ≈ 16.8 (model held by --load-mode none) + 3.5 (KV held by --no-kv-offload) + ~2 (OS). If none had "bypassed RAM," you wouldn't see a steady 22.5 GB after 10 minutes of runtime.
